# Классификация и обработка (processor.py)

Справочник по логике `services/processor.py`: как из сырья `raw_afl` получаются
`task_output`/`task_detail` (результат работы) и `task_report` (вид работ).
Правила выполняются строго по порядку — порядок = приоритет (первое сработавшее
«выигрывает», поэтому большинство условий требуют `IS NULL`).

## Общая схема пайплайна

```
xlsx (Алькор)
  └─ uploader.load_xlsx_to_raw    → raw_afl (колонки по порядку, без заголовков)
  └─ processor.process_raw_afl     → классификация + производные поля
  └─ merger.merge_to_main          → main_afl (INSERT новых / UPDATE пустых)
  └─ report_check.recompute_errors → main_afl.errors
```

`process_raw_afl` — последовательность SQL-`UPDATE` по `raw_afl`. После
рефакторинга (словари + data-driven) правила собраны в три списка:
- `TASK_OUTPUT_RULES` — результат (`task_output` / `task_detail`);
- `COMMENT_RULES` — проверки по `comment` (REGEXP);
- `TASK_REPORT_RULES` — вид работ (`task_report`).

Формат правила: `(SET-часть, WHERE-часть, progress)`; `progress` пишется в
`upload_progress` ПОСЛЕ правила (для прогресс-бара загрузки).

## Шаг 0. Предобработка
1. Удалить строки, чьё `executor_organization` отсутствует в `users.dept`.
2. Удалить строки с `task_number IS NULL`.
3. Переименования исполнителей (Жагорова → Загуменнова, «Петрова … (ПЭК)» → Петрова).

## Шаги 1–3. Производные поля
- **region** = первые 3 символа `municipal_district`.
- **grid** = из `visit_reason` (Python-функция `process_row`, словарь `NORM_MAP`).
- **customer** = `'ПСК'`, если `grid='-'`, иначе `'РЛЭ'`.

## Проверки по comment (REGEXP)
- «Объект не эксплуатируется» / «Объект отсутствует» — по `unsuccessful_inspection_reason`.
- `00` — «Несоответствие тарифных зон» (для `CHECK_WORK_TYPES`).
- Коды `11…99` (кроме 00) — для `work_type_in_task='Проверка, осмотр ПУ'` (словарь `VISIT_REASON_CODES`).
- `!!` — «Несоответствие разрядности»; `??` — «Неподключенный новый ввод».
- `77` — «Отсутствует тип ПУ в справочнике Алькора» (для допускных типов).
- «Нет доступа до ПУ» / «Помещение не найдено» — `Невозможно`.

## Шаги 6–7. Производные поля
- **task_report_id** = `work_end_date` (ГГГГ-ММ-ДД) + `-` + `metering_point` (для строк с `task_report`, кроме «Ручная проверка»).
- **created_at** переформатируется в `ГГГГ-ММ-ДД`.
- **Дедубликация**: для одинакового `task_report_id` остаётся самая свежая строка, остальные → `task_report='Дубли'`, `task_detail='Дубли'`.
- **Недопуск**: `task_output='Допуск'` + признаки нарушений → `task_detail='Недопуск ПУ'`.
- **Не исполнено 14**: `meter_type` и `meter_type_2` пусты И `task_report='Выявление безучетного потребления БП'` → `task_output='Не исполнено'`, `task_report=NULL`, `task_detail='14'`.
- **Бытовые заявки (ПСК)**: `task_report='Выявление безучетного потребления БП'` И `customer='ПСК'` → `task_report='Бытовые заявки'`.
- **done_day** = `work_end_date` (ГГГГ-ММ-ДД); **done_day_type** — из таблицы `calendar`.

## Группы признаков (словари)
Единый источник правды в `processor.py`:
`ADMISSION_WORK_TYPES`, `ADMISSION_WORK_TYPES_EXT`, `ADMISSION_WORK_TYPES_IN_TASK`,
`CHECK_WORK_TYPES`, `CONTROL_WORK_TYPES`, `UNMETERED_WORK_TYPES`, `VIOLATION_WORK_TYPES`,
`METER_STATUS_OK`, `METER_STATUS_BAD`, `MKD_OBJECT_TYPES`, `PLAN_INDOOR_PLACES`,
`DOMESTIC_PLACES`, `RESULT_OUTPUTS`, `NORM_MAP`, `VISIT_REASON_CODES`.

## Известные пробелы классификации
1. **Перепрограммирование ПУ с неисправным ПУ** (пример — задание `CP003445041`):
   `work_type_in_task='Перепрограммирование ПУ'` + `meter_status='Неисправен'` +
   `final_meter_status='Неисправен'` + `violations='Нет'` → не попадает ни в
   «Показания 13» (нужен `meter_status='Исправен'`), ни в «Восстановление учета»
   (нужен `final_meter_status='Исправен'`), ни в «Не исполнено». Проваливается в
   catch-all «Проверка 8» (`sent_to_billing='Да'`), а правила вида работ для
   «Перепрограммирование ПУ» с результатом «Проверка» нет → `task_report` пустой.
2. Пустой `task_report` у «Не исполнено» — **легитимно** (невыполненные работы).

## Примечание
Рефакторинг «словари + data-driven» (2026) дал построчно идентичный результат
старой реализации (сверка на 16 199 строках `raw_afl`) и не изменил время обработки
(≈2.1 с на том же объёме).
