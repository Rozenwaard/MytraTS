# Бизнес-логика MytraTS

Этот документ описывает **что делает система и по каким правилам** (домен, поток данных,
бизнес-правила). «Где что лежит» — см. `STATE.md` (структура, эндпоинты, конвенции, TODO).
Здесь — только смысл и правила.

---

## 1. Что это

Приложение управления реестрами заданий энергосбыта. Оператор загружает выгрузку
«Отчёт по заданиям ФЛ» из системы **Алькор** (Excel), система классифицирует строки,
проверяет их на ошибки, формирует **реестры** для сдачи и ведёт **архив** закрытых периодов.

Ключевые сущности:
- **Задание** — строка из выгрузки Алькора, идентифицируется `task_number`.
- **Реестр** — сгруппированный набор заданий с присвоенным номером (`reestr_number`), под сдачу.
- **Отчётный период** — месяц/год, по которому строки уходят в архив (`story_afl`).
- **Заказчик (customer)** — `ПСК` или `РЛЭ` (второй заказчик — в перспективе, см. `rle.py`).

## 2. Поток данных

```
xlsx (Алькор)
   │  uploader.load_xlsx_to_raw
   ▼
raw_afl            ── сырьё: колонки Excel сопоставлены по порядку (без заголовков)
   │  processor.process_raw_afl   (30+ SQL-шагов классификации)
   ▼
main_afl           ── рабочая таблица (+ errors, + reestr_number/reestr_date, + report)
   │
   ├─► reestr (формирование реестра)  → xlsx реестра
   │
   └─► report (формирование отчёта за месяц/год)
          ├─ строки с reestr_date → report = период
          ├─ строки 'Отклонён'    → report = 'Отклонён'
          └─ перенос в story_afl (архив), удаление из main_afl
```

Подробно по шагам — разделы ниже. Пошаговая логика классификации
(правила `task_output`/`task_detail`, `task_report`, производные поля, известные
пробелы) — в `КЛАССИФИКАЦИЯ-ОБРАБОТКИ.md`.

### Слияние в main_afl (services/merger.py)

После классификации строки переносятся из `raw_afl` в `main_afl`:

- строки со `status IS NULL` не переносятся (отбрасываются);
- строки с `task_number IS NULL` не переносятся (отбрасываются);
- строки с закрытым/завершённым статусом (`status LIKE 'З%'`) и `done_day IS NULL` не переносятся (отбрасываются);
- строки с новым `task_number` — вставляются;
- строки с существующим `task_number` перезаписываются, **кроме** тех, у которых уже
  присвоен номер реестра (`reestr_number` непустой и ≠ «Отклонён»), и строк с
  `task_detail = 'Разногласия'` — такие защищены от перезаписи;
- `reestr_number = 'Отклонён'` при перезаписи сбрасывается в пустой (строка заново доступна для реестра).

Ошибки (`recompute_errors`) пересчитываются только для вставленных/обновлённых строк.

## 3. Модель данных (таблицы)

| Таблица | Назначение |
|---|---|
| `raw_afl` | Сырая выгрузка Алькора (пересоздаётся при каждой загрузке). |
| `main_afl` | Рабочая таблица. + `errors`, `reestr_number`, `reestr_date`, `report`. |
| `story_afl` | Архив (перенесённые после формирования отчёта строки). |
| `calendar` | Календарь дней (`d`, `type`, `week`, `name`) — для `done_day_type` (рабочий/выходной). |
| `users` | Пользователи (`staff_id`, `role`, `dept`, `locale`, `position`, `settings`). |

Поля `main_afl` по группам:
- **паспорт задания**: `task_number`, `task_source`, `task_type`, `work_type_in_task`, `created_at`, `task_link`;
- **адрес/потребитель**: `address`, `municipal_district`, `house_type`, `personal_account`, `subscriber_name`, `service_object_type`, `metering_point`;
- **ПУ старое / новое** (суффиксы `_1`, `_2`): тип, модель, номер, год, поверка, разрядность, пломбы, показания `t1/t2/t3`, `meter_status`, `violations`;
- **итог работы**: `work_type`, `work_result`, `work_start_date`, `work_end_date`, `sent_to_billing`, `billing_sent_at`, `verified`, `executor`, `executor_organization`, `visit_reason`, `comment`, `acts`;
- **вычисляемое системой**: `customer`, `region`, `grid`, `task_output`, `task_detail`, `task_report`, `task_report_id`, `done_day`, `done_day_type`, `errors`, `reestr_number`, `reestr_date`, `report`.

Маппинг колонок Excel → поля: порядок колонок задан в `services/uploader.py` (`RAW_AFL_XLSX_COLUMNS`);
точечный маппинг букв колонок (BX→work_type, BQ→violations и т.д.) — в docstring `services/report_check.py`.

## 4. Классификация (services/processor.py)

`process_raw_afl` — каскад `UPDATE`-правил поверх `raw_afl`. Порядок шагов важен
(каждое правило срабатывает, только если поле ещё `NULL`). Прогресс пишется в `upload_progress`.

**Подготовка:**
- Регистрируется SQLite-функция `REGEXP` (для правил по комментарию).
- Удаляются строки, чьё отделение не из справочника `users`, и строки без `task_number`.
- Нормализуются ФИО исполнителей (2 точечные правки).

**Шаг 1 — region**: `region = первые 3 символа municipal_district` (например `СПб`).

**Шаг 2 — grid (сетевая)**: из `visit_reason` через `process_row` + `NORM_MAP`
(гтэс→ГтЭС, кнэс→КнЭС, нлэс→НлЭС, сэс→СЭС, тхэс/тхвэс→ТхЭС, юэс→ЮЭС, вэс→ВЭС).

**Шаг 3 — customer**: `grid = '-'` → `ПСК`, иначе → `РЛЭ`.

**Шаг 4 — task_output (результат) + task_detail (код/причина)** — каскад:
- статус не закрыт (`status NOT LIKE 'З%'`) → «В работе»;
- нет даты окончания → «Не исполнено»;
- «Невозможно» (осмотр невозможен), «Контроль» (Контроль СП, выполнено);
- «Допуск» (допуск/установка ПУ, по показаниям `t1_1` и `violations`) — коды 2/3;
- «Недопуск» («Допуск ПУ» + `meter_serial_number = meter_serial_number_2` + «невозможно выполнить допуск ПУ» + есть показания `t1`/`t1_1`);
- «Не исполнено» (несоблюдение процедуры допуска);
- «Показания» (по статусу ПУ и показаниям);
- «Проверка» (коды 6/7/8/10) и «Не исполнено 9»;
- **по комментарию через REGEXP**: коды `00` (тарифные зоны), `11..99` (список `VISIT_REASON_CODES`),
  `!!` (разрядность), `??` (новый ввод), `77` (нет типа ПУ в Алькоре);
- причины «Нет доступа до ПУ» / «Помещение не найдено» → «Невозможно».

**Шаг 5 — task_report (вид работ)** — каскад:
- «Периодический контроль БП» (Контроль);
- «Допуск ПУ в ИЖС» / «Допуск ПУ в МКД» (по `service_object_type`);
- «Выявление безучетного потребления БП» (инструментальная проверка);
- «Бытовые заявки» (внеплановые);
- «План ИЖС» / «План лестница» / «План квартира» (плановые осмотры, по объекту и месту установки).

**Шаг 6 — task_report_id**: `дата окончания работы + metering_point` — ключ дедупликации.
**Дедупликация**: для одинаковых `task_report_id` оставляется самая свежая строка,
остальным `task_report='Дубли'`, `task_detail='Дубли'`.

**Недопуск**: «Допуск» + есть нарушения (неисправность/вмешательство/подключение/доп.)
→ `task_detail='Недопуск ПУ'`.

**Шаг 7 — done_day**: `done_day = work_end_date` (ГГГГ-ММ-ДД), `done_day_type` из `calendar`.

> Список кодов `VISIT_REASON_CODES` (основание посещения) — в `services/processor.py`.

## 5. Проверка ошибок (services/report_check.py)

`check_row(row)` возвращает список ошибок; `recompute_errors` пересчитывает и сохраняет их
в `main_afl.errors` (разделитель `; `). Пересчёт — после загрузки, **для всех заказчиков**.

Всего **25 типов ошибок — все стоп-факторы** (включая 2 балансовые):

| Ошибка | Правило (кратко) | Тип |
|---|---|---|
| Дата работ | дата начала ≠ дата окончания работы | стоп |
| Зачем дата неисправности? | дата состояния ПУ заполнена, а нарушений нет | стоп |
| Дата неисправности | `violations='Да'` без даты; или дата не первое число месяца | стоп |
| Приложить акт | `violations='Да'` без акта | стоп |
| Год выпуска | год пуст / не 4 цифры / < 1959 | стоп |
| Дата поверки | поверка пуста/1899; или `01.01.2026` | стоп |
| Годы несовпадают | год поверки < год выпуска | стоп |
| Балансовая принадлежность | `meter_type` заполнен И старая принадлежность пуста/«не задано» | стоп (баланс) |
| Проверка на СП | активное отключение без акта ограничения | стоп |
| показания ДТ / НТ / Третий тариф | контрольные показания > расчётных | стоп |
| Показания ЭЦР | для ЭЦР-2400 T1 ≠ T2 | стоп |
| Тип ПУ | тип ПУ.2 содержит скобки/«мпи»/«лет» | стоп |
| Модель ПУ | модель ПУ.2 содержит «мпи»/«лет» | стоп |
| Разрядность | дробная часть ПУ.2 ≠ 0; или ИСУ целая ≠ 6 | стоп |
| Токи | ПУ.2 без номинального тока | стоп |
| Напряжение | ПУ.2 без номинального напряжения | стоп |
| Ручная проверка нарушения | заполнено несанкционированное подключение | стоп |
| ПУ допущен? | допуск: пломбы/показания не соответствуют результату | стоп |
| Не там введены показания | допуск выполнен, но `t1` заполнен | стоп |
| Пломба | восстановление учёта без пломб | стоп |
| Что с учетом? | распломбировка с заполненными пломбами | стоп |
| Год выпуска 2 | у ЭЦР-типов первые 2 цифры № ≠ год выпуска | стоп |
| Балансовая принадлежность нового ПУ | принадлежность нового ПУ не из списка | стоп (баланс) |

**Стоп-фактор** (`is_stop_blocked`):
- активен, если `region='СПб'` **или** `municipal_district='ЛО Гатчинский муниципальный район'`;
- и есть хотя бы одна ошибка (включая балансовые);
- такие строки **не попадают в реестр** (исключаются в `api_reestr`, возвращаются в `blocked`).

Две балансовые ошибки (`BALANCE_ERRORS`) дополнительно выносятся в отдельные отчёты дашборда.

## 6. Реестры (services/reestr.py + routers/reestr.py)

Выбор строк для реестра — на вкладке «Обзор»: кликом по строкам или кнопкой
«Выбрать всё» (менеджер/оператор/работник). «Выбрать всё» берёт все `task_number`
текущей фильтрации через `GET /api/main-afl/ids` (те же фильтры, что у `GET /api/main-afl`).

Поиск реестра: `GET /api/reestr/find?q=` — по № задания или лицевому счёту (точное
совпадение) возвращает `reestr_number` строки; список переключается на этот реестр и
показывает одну найденную строку. Если у строки реестра нет (пусто/«Отклонён») — ничего не выводится.

Формирование (`POST /api/reestr`, `task_numbers`):
1. Выбираются строки, **исключаются** заблокированные стоп-фактором (→ `blocked`).
2. **Группировка** по ключу `(executor_organization, customer, grid, task_report, locale)`,
   где `locale` берётся из `users.locale` по ФИО исполнителя.
3. **Номер реестра**: `prefix = DEPT_PREFIXES[отделение]`, `suffix = LOCALE_SUFFIXES[locale]`;
   номер = максимум существующих номеров с паттерном `%-{prefix}{suffix}%` + 1;
   итог: `"{номер}-{prefix}{suffix}"` (пример `12-Пш`).
4. **Отклонение**: если `task_report` пустой или в `{Дубли}` →
   `reestr_number='Отклонён'` (такие строки не нумеруются).
5. Строки, у которых реестр уже есть, помечаются как `skipped`.

Сброс (`POST /api/reestr/reset`): `reestr_number=NULL`, `reestr_date=NULL` для выбранных.

Выгрузка (`GET /api/download-reestr/{reestr_number}`): печатная форма реестра (xlsx) —
шапка «Реестр № … от …», строки (№ задания, л/с, район, адрес, дата), подписант —
«Начальник отделения» из `users` (или текущий пользователь, если не найден).

## 7. Формирование отчёта (routers/report.py)

`POST /api/report {month, year}` (только администратор/специалист):
1. `period = "{месяц} {год}"` (русское название месяца).
2. Строки с непустым `reestr_date` и пустым `report` → `report = period`.
3. Строки с `reestr_number='Отклонён'` и пустым `report` → `report='Отклонён'`.
4. Все строки с непустым `report` переносятся в `story_afl` и удаляются из `main_afl`.

`GET /api/download-report/{period}` — выгрузка полного отчёта периода (xlsx, все колонки).

Дополнительно — «Отчёты» → «Финотчёт» (пункт меню, только администратор; routers/fin_report.py):
- Плашки (с раскладкой по locale и суммой стоимости работ), все — только статус
  Завершено/Закрыто: «Заданий завершено» (status Завершено/Закрыто), «Исполнено
  без реестров» (нормальные виды работ без reestr_number), «Заданий с ошибками»
  (то же + непустой errors, в зоне стоп-фактора СПб+Гатчина), «Готово к отчёту»
  (есть номер реестра). «Нормальные виды работ» — `carte.kind='base'`. Сумма каждой
  плашки считается по расценкам carte.price (неизвестные виды работ = 0 ₽).
  Плашки учитывают выбранную область (см. ниже): без периода — только строки вне
  отчёта, с периодом — только строки этого периода.
- Окно «Период отчёта». По умолчанию — «Выберите период» (пусто): плашки и правая
  раскладка показывают строки, ещё не включённые в отчёт (`report IS NULL OR ''`),
  то есть текущую незакрытую работу. При выборе реального периода статистика
  переключается на него (`report = «ГГГГ ММ»`).
- «Добавить в отчёт» — видна всегда. Без выбранного периода кнопка разблокирована:
  проставляет `report = следующий период` (после последнего в main_afl) всем строкам
  «Готово к отчёту» (с реестром, не «Отклонён», пустым report). С выбранным периодом
  кнопка заблокирована до включения переключателя «Разблокировать»: проставляет
  `report = «ГГГГ ММ»` строкам с номером реестра (не «Отклонён»), пустым report и
  `done_day <= конец выбранного периода` (пустой done_day не попадает).
- «Разногласия» (txt, по одному task_number на строку, кодировка utf-8/cp1251) — для
  найденных по точному совпадению строк сбрасывает их в неисполненные:
  `task_report = NULL`, `task_detail = 'Разногласия'`, `reestr_number = 'Отклонён'`,
  `reestr_date = NULL`, `report = NULL`, `norm = NULL`, `extra = NULL`. Не найденные пропускаются (возвращается их число).
- Справа — раскладка завершённых строк (status Завершено/Закрыто) по нормальным
  видам работ в той же области (пусто → ещё не в отчёте; период → строки этого
  периода), общая стоимость (расценки carte.price, неизвестные = 0 ₽) и разбивка
  суммы на ПСК/РЛЭ (по полю customer).
- «Скачать отчёт» → `POST /fin-report/download` стартует фоновую генерацию (`download_id`);
  прогресс опрашивается `GET /fin-report/download/progress/{id}`, готовый ZIP отдаётся
  `GET /fin-report/download/result/{id}`. В ZIP — 6 файлов:
  - 4 detail по региону и типу (`спбплан`, `лоплан`, `спбвнеплан`, `ловнеплан`):
    строки `report = «ГГГГ ММ»`, все колонки кроме task_report_id/done_day/done_day_type/
    report/errors; даты дд.мм.гггг; grid → полное название сети (GRID_NAMES);
    task_report → нумерованный код (WORK_TYPE_CODES);
  - 2 допотчёта по плану (`спб`, `ло`) с 3 вкладками: «1.1 БП кварт» (План квартира) и
    «1.2 БП лестн» (План лестница) агрегированы по `municipal_district + адрес до «кв.»`
    (Кол-во снятых показаний = COUNT(*)); «1.3 БП частный сектор» (План ИЖС) — построчно.
    Колонки: Заказчик (customer), № п/п, Субъект РФ (region), Филиал Заказчика (grid →
    GRID_NAMES, пусто если нет), Адрес, Реквизиты (reestr_number + reestr_date, пусто
    если нет/«Отклонён»), Отделение/участок (executor_organization); в ИЖС дополнительно
    Абонентский номер (personal_account) и Дата проверки (done_day).

### Премия (вкладка «Отчёты» → «Премия», routers/premium.py)
Пока реализована только загрузка табеля и сводка по должностям (сам расчёт премии — отдельно).
- «Добавить табель» (xlsx/xls) парсится как в эталонном `timer()`: без шапки, убираются
  пустые строки/колонки; период в ячейке `(строка 2, колонка 6)` → нормализуется в
  `«ГГГГ ММ»` (с пробелом, как `report`); данные с 8-й строки; `col2` = табельный номер,
  `col3` = ФИО, `col4` = должность, `col5` = время вида `"18 (142,6)"`, где в скобках — часы.
- В таблицу `tabel(табельный номер, период, минуты, должность, ФИО)` пишутся только нужные
  должности: инженеры (все, кроме ведущих), контролёры, водители автомобиля — по должности
  из `col4` файла. Остальные должности не хранятся. Строки без часов (`часы = 0`) пропускаются.
  `минуты = часы × 60`.
- Плашки считаются по должности из файла (`tabel.position`): инженеры (все, кроме ведущих),
  контролёры, водители автомобиля. «Число» — разные табельные номера; «человекодни» —
  сумма минут / 480 (8-часовой день), округлённая до целого.
- Лица из `tabel`, отсутствующие в `users`, отдаются сводкой в `missing` (ФИО + должность +
  табельный номер), но **только по должностям инженер/контролёр** (водители не
  предупреждаются). Предупреждение показывается, пока такие лица не появятся в `users`
  (персистентное сравнение `tabel` ↔ `users`).
- Повторная загрузка того же периода заменяет его строки (DELETE + INSERT).
- Сводка `GET /premium/summary?period=`: список периодов + три плашки по выбранному
  периоду: «число» (разные табельные номера) и «человекодни» = сумма минут / 480
  (8-часовой день). В UI — выпадающий список периодов; по умолчанию — последний
  (самый свежий по календарю) период.
- Период в отчёте хранится с пробелом (`2026 07`) — это и есть консистентная конвенция;
  дефис (`2026-07`) используется только в UI-значениях селектора и в именах файлов.

### Нормативы и агрегация (вкладка «Премия», routers/premium.py + services/premium.py)
- Справочник `carte(id, title, absolute, price, kind, planned, detail)` — единый источник
  нормативов (значения — `Тарифы.xlsx`). `kind`: `base` (базовый) / `replacement`
  (замещающий) / `additional` (дополнительный); `planned` — норматив при
  `task_type='Плановый'` (NULL = как `absolute`); `detail` — `task_detail`, которым
  сопоставляется код/причина. Заполняется `_migrate_premium.py` + `_migrate_norm.py`.
  Цена — `carte.price` (₽), единый источник цен для стоимости в дашборде и финотчёте.
- Норматив проставляется **по факту загрузки строки** (в `merger.py` вызовом `apply_norms()`)
  в две INTEGER-колонки: `main_afl.norm` — база (основной вид работ), `main_afl.extra` —
  доп. («Код …», «Причина…», «+5 Выполнение задания в Алькоре»). Номер реестра лишь
  защищает строку от перезаписи (и норматив — от переопределения). Правила — `services/premium.py`:
  - базовый тариф → `norm` (`carte.kind='base'` по `task_report`); для `Выявление безучетного
    потребления БП` — 40 (МКД) / 60 (ИЖС) по `service_object_type`;
  - замещающие тарифы (`kind='replacement'`, по `detail = task_detail`) → `norm=0`, `extra=тариф`:
    Код 11/33/44/55/66 → 20 (Плановый → 10), Код 77/88/99 → 20 (Плановый → 0), «Нет доступа» → 5
    (Плановый → 0), «Расселённая квартира» (`Объект не эксплуатируется`) и «Здание снесено»
    (`Объект отсутствует`) → 20 (Плановый → 10), «Помещение не найдено» → 5 (Плановый → 0);
  - дополнительные тарифы (`kind='additional'`, по `detail = task_detail`) → `extra += тариф`:
    Код 00 → +5, Код 22 → +15, Код !! → +5;
  - «Выполнение задания в Алькоре» → `extra += 5` строкам с нормативом, кроме `Дубли`/`Ручная правка`;
  - `Дубли` и `Ручная правка` → `norm=0`, `extra=0`.
- Смена вида работ (`PATCH /api/main-afl/task-report`) считает норматив от нового
  `task_report` (`norm` = база, `extra` = +5) через `apply_manual_norm`.
- «Отчёт по нормативам» (`POST /api/premium/norms`) агрегирует все строки `main_afl`
  (`norm != 0` или `extra != 0`) в `utalo(период, табельный номер, ФИО, должность, депт,
  вид работ, количество, сумма норматива)`: база → строка с видом `task_report` и суммой
  `norm`, доп. → строка с видом = источник extra («Код …» или «Выполнение задания в Алькоре»)
  и суммой `extra`.
- «Скачать отчёт» (`GET /api/premium/download?period=YYYY MM`) выгружает из `utalo` за период
  xlsx с двумя вкладками: «Алькор» (вид ∈ `carte.kind='base'`) и «Проект» (остальные источники).
  Колонки: ФИО, должность, отделение, работа, количество, норматив.

### РЛЭ (вкладка «Отчёты», routers/rle.py + services/rle.py)
Недельный отчёт по заказчику РЛЭ (методика — эталонный `feel.xlsx`). Считается по
`main_afl` (строкам с `done_day`); неделю берём из `calendar` (join `calendar.d = done_day`).
- Недели идут с 27-й (начало производственного года, июль) до последней полной недели
  на момент запроса (последняя неделя, чей последний день уже прошёл).
- На каждую неделю: минуты заказчиков = `SUM(COALESCE(norm,0)+COALESCE(extra,0))`
  (ПСК и РЛЭ), число исполнителей = `COUNT(DISTINCT executor)` по неделе,
  `исполнителей для РЛЭ = исполнителей × (минуты РЛЭ / минуты всего)`.
- По каждой сети (`grid`, customer='РЛЭ'): минуты = `SUM(norm+extra)`, доля = минуты / РЛЭ,
  «исполнителей сети» = доля × исполнителей для РЛЭ; работ = `COUNT(task_report)`
  (исключая `task_report IN ('Дубли','Ручная проверка')`).
- Блок недели (3 колонки на сеть): «Работы» = работ; «Удельно» = работ / исполнителей
  сети; «В день» = удельно / 5 (рабочая неделя). Дробные значения — 1 знак после запятой.
- Таблица: сквозная колонка «Филиал» (сети) + недельные блоки; итоговая строка
  «Всего работ» + «Работников» на каждую неделю.
- Во вкладке показываются последние 5 недель; над таблицей — плашки max/min
  (Работников / Работ / В день) за весь период. Скачивание — весь период (с 27-й недели).
- `GET /api/rle` — JSON для вкладки; `GET /api/rle/download` — xlsx за весь период
  (файл «РЛЭ неделя N.xlsx», N — последняя неделя).

## 8. Роли и права

5 ролей (`data/models.py`, `ROLES`): администратор, специалист, менеджер, оператор, работник.

`User.effective_role` = явное `users.role`, либо `derived_role` (fallback):
- `dept='Отдел организации'` + `position='Директор'` → администратор;
- `dept='Отдел организации'` → специалист;
- `position='Начальник отделения'` → менеджер;
- иначе → оператор.

**Видимость данных** (в фильтрах везде):
- **оператор / работник** — только свои: `executor IN (SELECT full_name FROM users WHERE locale = :locale)`;
- **менеджер** — своё отделение: `executor_organization = :dept`;
- **администратор / специалист** — всё.

**Права действий:**
- Формирование отчёта, отклонение строк архива, смена вида работ (`task-report`) — только администратор/специалист.
- Кнопки дашборда «Балансовая принадлежность», «Дата работ», «Отметка о проверке» — только администратор/специалист.

## 9. Дашборд (services/dashboard.py + routers/dashboard.py)

Две вкладки:

### «Обзор» (`/api/dashboard/overview`)

Общая сводка по завершённым (status Завершено/Закрыто) строкам **без отчёта** (`report`
пуст) в зоне видимости пользователя (без фильтра `customer`/территория/виды работ, как
в `/api/main-afl/stats`). Лента плашек:

- **Заданий** — число завершённых строк;
- **ПСК / РЛЭ** — по `customer`;
- **План / Внеплан** — по `task_type`;
- **Выполнено / Не выполнено** — `task_report` заполнен и не в {Дубли};
- **С ошибками / Без ошибок** — из «выполнено», по `errors`;
- **Стоимость** — Σ расценки по `task_report` (`carte.price`) — совпадает со стоимостью
  плашки «Завершено» в Финотчёте.

### «Ошибки»

Зона/scope (`build_scope`): виды работ из `carte.kind='base'`
+ территории стоп-фактора + видимость по роли (+ фильтр отделения для админа).

Срезы (карточки):
- **в зоне** — строки зоны;
- **с ошибками** — строки с непустым `errors`;
- **отправлено в биллинг** — из строк с ошибками, `sent_to_billing='Да'`;
- **на исправлении** — из строк с ошибками, `sent_to_billing='Нет'` и `status != 'Закрыто'`;
- **всего ошибок** — сумма ошибок по строкам «на исправлении».

Расклад по видам ошибок — из строк «на исправлении».

Выгрузки (4 кнопки), все — **зона + `sent_to_billing='Нет'` и `status != 'Закрыто'`** (только «на исправлении»):
1. «Отчёт об ошибках» — № задания + ошибки, без балансовых и «Дата работ» (видна всем);
2. «Балансовая принадлежность» — № задания + тип ПУ (по балансовой ошибке);
3. «Дата работ» — только № задания (по ошибке «Дата работ»);
4. «Отметка о проверке» — только № задания (`verified='Нет'`).

## 10. Ключевые термины (глоссарий)

- **task_output** — результат работы: В работе / Не исполнено / Невозможно / Контроль / Допуск / Проверка / Показания / Нарушение.
- **task_detail** — код/причина результата (цифры `0..14` или текст причины).
- **task_report** — вид работ (base-тарифы `carte` + служебные «Дубли»).
- **customer** — заказчик: ПСК / РЛЭ.
- **grid** — сетевая (нормализованное имя из основания посещения).
- **region** — первые 3 символа `municipal_district`.
- **sent_to_billing** — «Отправлено в биллинг» (Да/Нет).
- **verified** — «Проверено» (Да/Нет).
- **errors** — найденные ошибки через `; `.
- **reestr_number / reestr_date** — присвоенный номер реестра и дата.
- **report** — отчётный период («месяц год») или «Отклонён»; непустой ⇒ строка ушла в архив.
- **стоп-фактор** — не-балансовая ошибка, блокирующая реестр в зоне СПб/Гатчинский.
