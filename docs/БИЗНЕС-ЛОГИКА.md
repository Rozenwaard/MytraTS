# Бизнес-логика MytraTS

Этот документ описывает **что делает система и по каким правилам** (домен, поток данных,
бизнес-правила). «Где что лежит» — см. `STATE.md` (структура, эндпоинты, конвенции, TODO).
Здесь — только смысл и правила.

---

## 1. Что это

Приложение управления реестрами заданий энергосбыта. Оператор загружает выгрузку
«Отчёт по заданиям ФЛ» из системы **Алькор** (Excel), система классифицирует строки,
проверяет их на ошибки, формирует **реестры** для сдачи и ведёт **архив** закрытых периодов.

Ключевые сущности:
- **Задание** — строка из выгрузки Алькора, идентифицируется `task_number`.
- **Реестр** — сгруппированный набор заданий с присвоенным номером (`reestr_number`), под сдачу.
- **Отчётный период** — месяц/год, по которому строки уходят в архив (`story_afl`).
- **Заказчик (customer)** — `ПСК` или `РЛЭ` (второй заказчик — в перспективе, см. `rle.py`).

---

## 2. Поток данных

```
xlsx (Алькор)
   │  uploader.load_xlsx_to_raw
   ▼
raw_afl            ── сырьё: колонки Excel сопоставлены по порядку (без заголовков)
   │  processor.process_raw_afl   (30+ SQL-шагов классификации)
   ▼
main_afl           ── рабочая таблица (+ errors, + reestr_number/reestr_date, + report)
   │
   ├─► reestr (формирование реестра)  → xlsx реестра
   │
   └─► report (формирование отчёта за месяц/год)
          ├─ строки с reestr_date → report = период
          ├─ строки 'Отклонён'    → report = 'Отклонён'
          └─ перенос в story_afl (архив), удаление из main_afl
```

Подробно по шагам — разделы ниже.

### Слияние в main_afl (services/merger.py)

После классификации строки переносятся из `raw_afl` в `main_afl`:

- строки с новым `task_number` — вставляются;
- строки с существующим `task_number` перезаписываются, **кроме** тех, у которых уже
  присвоен номер реестра (`reestr_number` непустой и ≠ «Отклонён») — такие защищены от перезаписи;
- `reestr_number = 'Отклонён'` при перезаписи сбрасывается в пустой (строка заново доступна для реестра).

Ошибки (`recompute_errors`) пересчитываются только для вставленных/обновлённых строк.

## 3. Модель данных (таблицы)

| Таблица | Назначение |
|---|---|
| `raw_afl` | Сырая выгрузка Алькора (пересоздаётся при каждой загрузке). |
| `main_afl` | Рабочая таблица. + `errors`, `reestr_number`, `reestr_date`, `report`. |
| `story_afl` | Архив (перенесённые после формирования отчёта строки). |
| `calendar` | Календарь дней (`d`, `type`, `week`, `name`) — для `done_day_type` (рабочий/выходной). |
| `users` | Пользователи (`staff_id`, `role`, `dept`, `locale`, `position`, `settings`). |

Поля `main_afl` по группам:
- **паспорт задания**: `task_number`, `task_source`, `task_type`, `work_type_in_task`, `created_at`, `task_link`;
- **адрес/потребитель**: `address`, `municipal_district`, `house_type`, `personal_account`, `subscriber_name`, `service_object_type`, `metering_point`;
- **ПУ старое / новое** (суффиксы `_1`, `_2`): тип, модель, номер, год, поверка, разрядность, пломбы, показания `t1/t2/t3`, `meter_status`, `violations`;
- **итог работы**: `work_type`, `work_result`, `work_start_date`, `work_end_date`, `sent_to_billing`, `billing_sent_at`, `verified`, `executor`, `executor_organization`, `visit_reason`, `comment`, `acts`;
- **вычисляемое системой**: `customer`, `region`, `grid`, `task_output`, `task_detail`, `task_report`, `task_report_id`, `done_day`, `done_day_type`, `errors`, `reestr_number`, `reestr_date`, `report`.

Маппинг колонок Excel → поля: порядок колонок задан в `services/uploader.py` (`RAW_AFL_XLSX_COLUMNS`);
точечный маппинг букв колонок (BX→work_type, BQ→violations и т.д.) — в docstring `services/report_check.py`.

## 4. Классификация (services/processor.py)

`process_raw_afl` — каскад `UPDATE`-правил поверх `raw_afl`. Порядок шагов важен
(каждое правило срабатывает, только если поле ещё `NULL`). Прогресс пишется в `upload_progress`.

**Подготовка:**
- Регистрируется SQLite-функция `REGEXP` (для правил по комментарию).
- Удаляются строки, чьё отделение не из справочника `users`, и строки без `task_number`.
- Нормализуются ФИО исполнителей (2 точечные правки).

**Шаг 1 — region**: `region = первые 3 символа municipal_district` (например `СПб`).

**Шаг 2 — grid (сетевая)**: из `visit_reason` через `process_row` + `NORM_MAP`
(гтэс→ГтЭС, кнэс→КнЭС, нлэс→НлЭС, сэс→СЭС, тхэс/тхвэс→ТхЭС, юэс→ЮЭС, вэс→ВЭС).

**Шаг 3 — customer**: `grid = '-'` → `ПСК`, иначе → `РЛЭ`.

**Шаг 4 — task_output (результат) + task_detail (код/причина)** — каскад:
- статус не закрыт (`status NOT LIKE 'З%'`) → «В работе»;
- нет даты окончания → «Не исполнено»;
- «Невозможно» (осмотр невозможен), «Контроль» (Контроль СП, выполнено);
- «Допуск» (допуск/установка ПУ, по показаниям `t1_1` и `violations`) — коды 2/3;
- «Не исполнено» (несоблюдение процедуры допуска);
- «Показания» (по статусу ПУ и показаниям);
- «Проверка» (коды 6/7/8/10) и «Не исполнено 9»;
- **по комментарию через REGEXP**: коды `00` (тарифные зоны), `11..99` (список `VISIT_REASON_CODES`),
  `!!` (разрядность), `??` (новый ввод), `77` (нет типа ПУ в Алькоре);
- причины «Нет доступа до ПУ» / «Помещение не найдено» → «Невозможно».

**Шаг 5 — task_report (вид работ)** — каскад:
- «Периодический контроль БП» (Контроль);
- «Допуск ПУ в ИЖС» / «Допуск ПУ в МКД» (по `service_object_type`);
- «Выявление безучетного потребления БП» (инструментальная проверка);
- «Бытовые заявки» (внеплановые);
- «План ИЖС» / «План лестница» / «План квартира» (плановые осмотры, по объекту и месту установки);
- «Ручная проверка» (допуск/установка, если не подошло ни одно правило).

**Шаг 6 — task_report_id**: `дата окончания работы + metering_point` — ключ дедупликации.
**Дедупликация**: для одинаковых `task_report_id` оставляется самая свежая строка,
остальным `task_report='Дубли'`, `task_detail='Дубли'`.

**Недопуск**: «Допуск» + есть нарушения (неисправность/вмешательство/подключение/доп.)
→ `task_detail='Недопуск ПУ'`.

**Шаг 7 — done_day**: `done_day = work_end_date` (ГГГГ-ММ-ДД), `done_day_type` из `calendar`.

> Список кодов `VISIT_REASON_CODES` (основание посещения) — в `services/processor.py`.

## 5. Проверка ошибок (services/report_check.py)

`check_row(row)` возвращает список ошибок; `recompute_errors` пересчитывает и сохраняет их
в `main_afl.errors` (разделитель `; `). Пересчёт — после загрузки, **только для строк `customer='ПСК'`**.

Всего **25 типов ошибок = 23 стоп-фактора + 2 балансовых**:

| Ошибка | Правило (кратко) | Тип |
|---|---|---|
| Дата работ | дата начала ≠ дата окончания работы | стоп |
| Зачем дата неисправности? | дата состояния ПУ заполнена, а нарушений нет | стоп |
| Дата неисправности | `violations='Да'` без даты; или дата не первое число месяца | стоп |
| Приложить акт | `violations='Да'` без акта | стоп |
| Год выпуска | год пуст / не 4 цифры / < 1959 | стоп |
| Дата поверки | поверка пуста/1899; или `01.01.2026` | стоп |
| Годы несовпадают | год поверки < год выпуска | стоп |
| Балансовая принадлежность | старая принадлежность пуста/«не задано» | **баланс** |
| Проверка на СП | активное отключение без акта ограничения | стоп |
| показания ДТ / НТ / Третий тариф | контрольные показания > расчётных | стоп |
| Показания ЭЦР | для ЭЦР-2400 T1 ≠ T2 | стоп |
| Тип ПУ | тип ПУ.2 содержит скобки/«мпи»/«лет» | стоп |
| Модель ПУ | модель ПУ.2 содержит «мпи»/«лет» | стоп |
| Разрядность | дробная часть ПУ.2 ≠ 0; или ИСУ целая ≠ 6 | стоп |
| Токи | ПУ.2 без номинального тока | стоп |
| Напряжение | ПУ.2 без номинального напряжения | стоп |
| Ручная проверка нарушения | заполнено несанкционированное подключение | стоп |
| ПУ допущен? | допуск: пломбы/показания не соответствуют результату | стоп |
| Не там введены показания | допуск выполнен, но `t1` заполнен | стоп |
| Пломба | восстановление учёта без пломб | стоп |
| Что с учетом? | распломбировка с заполненными пломбами | стоп |
| Год выпуска 2 | у ЭЦР-типов первые 2 цифры № ≠ год выпуска | стоп |
| Балансовая принадлежность нового ПУ | принадлежность нового ПУ не из списка | **баланс** |

**Стоп-фактор** (`is_stop_blocked`):
- активен, если `region='СПб'` **или** `municipal_district='ЛО Гатчинский муниципальный район'`;
- и есть хотя бы одна **не-балансовая** ошибка;
- такие строки **не попадают в реестр** (исключаются в `api_reestr`, возвращаются в `blocked`).

Две балансовые ошибки (`BALANCE_ERRORS`) — **не блокируют** реестр.

## 6. Реестры (services/reestr.py + routers/reestr.py)

Формирование (`POST /api/reestr`, `task_numbers`):
1. Выбираются строки, **исключаются** заблокированные стоп-фактором (→ `blocked`).
2. **Группировка** по ключу `(executor_organization, customer, grid, task_report, locale)`,
   где `locale` берётся из `users.locale` по ФИО исполнителя.
3. **Номер реестра**: `prefix = DEPT_PREFIXES[отделение]`, `suffix = LOCALE_SUFFIXES[locale]`;
   номер = максимум существующих номеров с паттерном `%-{prefix}{suffix}%` + 1;
   итог: `"{номер}-{prefix}{suffix}"` (пример `12-Пш`).
4. **Отклонение**: если `task_report` пустой или в `{Дубли, Ручная проверка}` →
   `reestr_number='Отклонён'` (такие строки не нумеруются).
5. Строки, у которых реестр уже есть, помечаются как `skipped`.

Сброс (`POST /api/reestr/reset`): `reestr_number=NULL`, `reestr_date=NULL` для выбранных.

Выгрузка (`GET /api/download-reestr/{reestr_number}`): печатная форма реестра (xlsx) —
шапка «Реестр № … от …», строки (№ задания, л/с, район, адрес, дата), подписант —
«Начальник отделения» из `users` (или текущий пользователь, если не найден).

## 7. Формирование отчёта (routers/report.py)

`POST /api/report {month, year}` (только администратор/специалист):
1. `period = "{месяц} {год}"` (русское название месяца).
2. Строки с непустым `reestr_date` и пустым `report` → `report = period`.
3. Строки с `reestr_number='Отклонён'` и пустым `report` → `report='Отклонён'`.
4. Все строки с непустым `report` переносятся в `story_afl` и удаляются из `main_afl`.

`GET /api/download-report/{period}` — выгрузка полного отчёта периода (xlsx, все колонки).

## 8. Роли и права

5 ролей (`data/models.py`, `ROLES`): администратор, специалист, менеджер, оператор, работник.

`User.effective_role` = явное `users.role`, либо `derived_role` (fallback):
- `dept='Отдел организации'` + `position='Директор'` → администратор;
- `dept='Отдел организации'` → специалист;
- `position='Начальник отделения'` → менеджер;
- иначе → оператор.

**Видимость данных** (в фильтрах везде):
- **оператор / работник** — только свои: `executor IN (SELECT full_name FROM users WHERE locale = :locale)`;
- **менеджер** — своё отделение: `executor_organization = :dept`;
- **администратор / специалист** — всё.

**Права действий:**
- Формирование отчёта, отклонение строк архива, смена вида работ (`task-report`) — только администратор/специалист.
- Кнопки дашборда «Балансовая принадлежность», «Дата работ», «Отметка о проверке» — только администратор/специалист.

## 9. Дашборд (services/dashboard.py + routers/dashboard.py)

Две вкладки:

### «Обзор» (`/api/dashboard/overview`)

Общая сводка по всем строкам в зоне видимости пользователя (без фильтра
`customer`/территория/виды работ, как в `/api/main-afl/stats`). Лента плашек:

- **Заданий** — число строк;
- **ПСК / РЛЭ** — по `customer`;
- **План / Внеплан** — по `task_type`;
- **Выполнено / Не выполнено** — `task_report` заполнен и не в {Дубли, Ручная проверка};
- **С ошибками / Без ошибок** — из «выполнено», по `errors`;
- **Стоимость** — из «без ошибок»: Σ расценки по `task_report`
  (`WORK_TYPE_RATES` в services/dashboard.py).

### «Ошибки»

Зона/scope (`build_scope`): `customer='ПСК'` + 10 видов работ (`DASHBOARD_WORK_TYPES`)
+ территории стоп-фактора + видимость по роли (+ фильтр отделения для админа).

Срезы (карточки):
- **в зоне** — строки зоны;
- **с ошибками** — строки с непустым `errors`;
- **отправлено в биллинг** — из строк с ошибками, `sent_to_billing='Да'`;
- **на исправлении** — из строк с ошибками, `sent_to_billing='Нет'`;
- **всего ошибок** — сумма ошибок по строкам «на исправлении».

Расклад по видам ошибок — из строк «на исправлении».

Выгрузки (4 кнопки), все — **зона + `sent_to_billing='Нет'`** (только «на исправлении»):
1. «Отчёт об ошибках» — № задания + ошибки (видна всем);
2. «Балансовая принадлежность» — № задания + тип ПУ (по балансовой ошибке);
3. «Дата работ» — только № задания (по ошибке «Дата работ»);
4. «Отметка о проверке» — только № задания (`verified='Нет'`).

## 10. Ключевые термины (глоссарий)

- **task_output** — результат работы: В работе / Не исполнено / Невозможно / Контроль / Допуск / Проверка / Показания / Нарушение.
- **task_detail** — код/причина результата (цифры `0..14` или текст причины).
- **task_report** — вид работ (10 типов для дашборда/отчётов + служебные «Дубли», «Ручная проверка»).
- **customer** — заказчик: ПСК / РЛЭ.
- **grid** — сетевая (нормализованное имя из основания посещения).
- **region** — первые 3 символа `municipal_district`.
- **sent_to_billing** — «Отправлено в биллинг» (Да/Нет).
- **verified** — «Проверено» (Да/Нет).
- **errors** — найденные ошибки через `; `.
- **reestr_number / reestr_date** — присвоенный номер реестра и дата.
- **report** — отчётный период («месяц год») или «Отклонён»; непустой ⇒ строка ушла в архив.
- **стоп-фактор** — не-балансовая ошибка, блокирующая реестр в зоне СПб/Гатчинский.
